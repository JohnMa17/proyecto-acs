1. Introducción: La Naturaleza del Cambio

"Cualquier cambio, incluso para mejorar, está acompañado de inconvenientes e incomodidades."
— Arnold Bennett

En cualquier proyecto de software, el cambio es una certeza. Surgen modificaciones en las necesidades de negocio, correcciones en el código o ajustes en la infraestructura. Sin una disciplina formal, estos cambios provocan versiones inconsistentes, pérdidas de código y fallas de calidad.

La Administración de la Configuración del Software (ACS) proporciona el marco de trabajo y las herramientas necesarias para responder a cuatro objetivos esenciales:

1. Identificar

Reconocer todos los elementos discretos que componen la configuración del sistema.

2. Gestionar

Administrar las peticiones, impactos y modificaciones aplicadas a los componentes.

3. Facilitar

Permitir la construcción y ensamblaje de múltiples versiones del software de manera controlada.

4. Garantizar

Asegurar que la calidad y estabilidad se preserven a medida que el software evoluciona.

2. Las Capas Concéntricas del Proceso ACS

Según Pressman, los Ítems de Configuración del Software (ICS) se desplazan a través de capas concéntricas durante su ciclo de vida:

Los objetos que componen el software se catalogan con un nombre único y atributos definidos:

  • Objetos Básicos: Unidades atómicas creadas durante el ciclo de vida (ej. un módulo de código fuente, un caso de prueba, una sección de requisitos).
  • Objetos Agregados: Colecciones estructuradas de objetos básicos u otros agregados (ej. un documento de especificación técnica o un paquete de despliegue).
  • Relaciones Transestructurales: Conexiones de dependencia que permiten evaluar cómo la modificación de un objeto repercute en los demás.

Combina herramientas y procedimientos para gestionar las distintas versiones de los objetos de configuración. Integra el repositorio del proyecto, facilidades de compilación/construcción y herramientas de rastreo de diferencias (como los conjuntos de cambio o change sets, que describen quién, cuándo y por qué modificó cada archivo).

Establece el equilibrio crítico: evitar la burocracia que paraliza el avance sin caer en la anarquía del cambio descontrolado. Regula el proceso a través de la evaluación de peticiones, la intervención de la Autoridad de Control de Cambio (ACC) y la emisión de Órdenes de Cambio de Ingeniería (OCI).

Complementa las revisiones técnicas evaluando la conformidad del proceso: ¿Se implementó estrictamente lo aprobado en la OCI? ¿Se documentaron las fechas y los autores? ¿Se mantuvieron sincronizados todos los ítems vinculados?

También llamado contabilidad de estado. Es el mecanismo de comunicación que responde: ¿Qué cambió? ¿Quién lo autorizó y realizó? ¿Cuándo ocurrió? ¿Qué otros componentes fueron afectados? Garantiza la transparencia total ante el equipo y los interesados.

3. Flujo Operativo del Control de Cambio

1. Reconocimiento de necesidad y solicitud formal
↓
2. Evaluación técnica de impacto colateral y costos
↓
3. Decisión de la Autoridad de Control de Cambio (ACC)
↓ (Si se aprueba)
4. Emisión de Orden de Cambio de Ingeniería (OCI)
↓
5. Check-out del ICS & Desarrollo en entorno aislado
↓
6. Auditoría, pruebas de SQA e incorporación a la Línea Base

4. Correspondencia Práctica: Pressman vs. Ecosistema Git/GitHub

Concepto Teórico (Pressman) Mecanismo en Git / GitHub Función y Aplicación en Desarrollo Real
Ítem de Configuración (ICS) Archivos rastreados por Git (Tracked Files) Código, estilos, imágenes y documentación gestionados individualmente.
Línea de Referencia (Baseline) Rama main / Git Tags (ej. v1.0) Punto congelado y verificado que representa una entrega estable.
Aislamiento de Cambios Ramas de trabajo (Feature Branches) Permite desarrollo no lineal y paralelo sin interferir con la versión principal.
Solicitud / OCI Issues y Pull Requests (PR) Mecanismo donde se propone el cambio y se detalla su alcance.
Autoridad de Control (ACC) Revisores de Código (Code Reviewers) Valoran el PR, solicitan cambios y aprueban el Merge.
Auditoría y REC git log, git blame, GitHub Actions Trazabilidad inmutable de autores, fechas, mensajes de commit y pruebas.
